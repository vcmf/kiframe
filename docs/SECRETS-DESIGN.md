# Secrets pipeline: design (v0)

Status: **final, design-reviewed** (2026-09-28; draft 5 passed with no severe finding). Replaces the M1-5 field binding and the M1-6 scanner timing rules. APPROACHES §7.4 states the goals; this document is the contract the code must keep. Every rule has an id (`I…`, `A…`, `R…`) that tests and code comments refer to. Design reviews of draft 1 (15 findings, 8 severe), draft 2 (10 findings, 4 severe) and draft 3 (2 severe, 2 moderate) draft 4 (1 severe, 1 moderate) and draft 5 (1 moderate) are folded in. Draft 2 let a healed target keep its grant through an element signature; that signature was too weak on pages with bare inputs, so draft 3 binds the exact target and asks again after healing.

Why a redesign: M1-5 and M1-6 each needed three severe review rounds. Secret handling was spread over the runner, the vault, the recorder and the compositor with no written rules; the field binding was inferred from the DOM; the scanner's timing was patched hole by hole, and the compositor had timing rules of its own.

## 1. Threat model

**Assets.** Secret values (kinds `password`, `username`, `api_key`, `text`) and saved sessions (cookies, storage).

**Adversaries.**
- **A1, the agent:** confused or prompt-injected (by page content, a document, a chat message). It writes scenarios, presets, interrupt rules and compositions, and calls tools. It must never learn a value, nor get one typed, copied or shown where the user didn't approve.
- **A2, a hostile or buggy page:** any page the browser shows (iframes, redirects, popups). It can run JavaScript, change its DOM, move focus, navigate and spy on DOM APIs.
- **A3, artifact readers:** anyone who gets a take, a log, an error, a project folder (fingerprint crops included), git history, an export, or what the LLM provider (or our proxy) receives.
- **A4, viewers** of the final video, guide or screenshots.

**Out of the threat model.** Malware running as the user (it can read the keychain); the target app receiving the secret it's meant to receive and what it does with it (a hostile *same-origin* app can also display it in ways no scanner recognizes: I4 against it is best effort, §6); a user who approves a clearly worded bad request.

## 2. Invariants

- **I1, confinement.** A value exists only in the keychain, the vault's memory while resolving, the runtime's memory for the run (the *known values*), and the approved element's value. Never in the agent's or the LLM's context, in project, scenario, composition, take or history files (fingerprint crops included), in events, logs, errors or warnings, in URLs, in the OS clipboard, or in page JavaScript other than through the approved element.
- **I2, authorization.** A value is written only as §3 allows: an approved step with its exact approved target, on an approved page, into the element that target resolves to (checked against the approved element), through a handle to that element.
- **I3, scrubbing.** Every string that leaves the runtime (events, errors, warnings, tool results, navigate URLs, reports) passes through the scrubber with every known value.
- **I4, visual.** No rendered frame and no model screenshot shows a known value unblurred, within the scanner's scope (§5). Where the runtime can't tell, it hides more (§5 R7), never less. Secret masks are derived from the take at render time and can't be removed or shortened by editing a composition.
- **I5, storage.** Sessions live in memory for one batch. Raw takes are sensitive: only in the take store (M1-8, encrypted at rest), never exported, never in git. Fingerprint crops of secret targets are taken before the write (§5 R9).
- **I6, browser.** Off-the-record contexts only; no Playwright traces; no JavaScript steps.

## 3. Authorization

**A1, grants.** A grant is `{ scope, step key, secret, path pattern, target, element }`, stored **in the vault's metadata** (local, per user, per machine). Only the host's approval UI creates grants, from the user's answer; nothing the agent writes can (no project, scenario or composition field holds or names one).
- **Scope:** the id the host assigned to the project folder and keeps outside it (a `project.json` id the agent could copy is never trusted); for an org interrupt rule, the org (one grant covers every project of the org).
- **Step key:** `scene:<sceneId>/<phase>/<stepId>`, `preset:<name>/<stepId>` (one grant serves every scene using the preset), `interrupt:<ruleId>` or `org:<orgId>/interrupt:<ruleId>` (a project rule never satisfies an org rule's grant). The scene part is the host's id for the scene, kept outside the project (a deleted scene's replacement gets a new one even if the agent reuses its ids); without the host's project scope or scene id, a secret use is refused (never a shared default). A `type` step with a secret reference must have an id, in every phase (schema rule).
- **Path pattern:** the page's pathname when approved, normalized: numeric, UUID and long hex segments become `*` (`/projects/8123/settings` → `/projects/*/settings`); query and hash dropped. The prompt shows the pattern; the user can widen it. Interrupt grants: every path on the origin (a "Session expired" modal shows anywhere).
- **Target:** the step's target exactly as approved (canonical JSON, healing metadata `intent` / `fingerprint` left out). **Healing or re-grounding a secret-typing target asks again** (interactive runs) or fails (headless): a grant covers what the user saw, nothing inferred.
- **Element:** what the target resolved to at approval: tag, `type`, and its label (the accessible name from a `<label>`, `aria-label` or `aria-labelledby`; a name that comes only from a `placeholder` isn't compared, apps localize or change it). Checked at run time too (defense in depth: the same locator on a changed page may reach another field); a mismatch asks again (interactive) or fails (headless).
- **Nothing page-derived in the clear:** the path pattern's literal segments and the element's label are stored as keyed hashes (HMAC-SHA256 with a random key the vault keeps in the keychain), so a value the page shows in its URL or a label never lands in `vault.json`. Matching hashes the use the same way (one keychain read for the key, kept in memory). The prompt shows the user the plain path pattern and label at approval time; the vault UI shows a grant's step, origin and target.
- **Origin:** the page's origin, one of the secret's origins.

**A2, at run time.** The target must match **exactly one** visible element (no fallbacks and no `nth` for secret-typing steps: schema rule). The runtime asks the vault with the use `{ scope, step key, secret, origin, path, target, element }`; the vault refuses (`secret-refused`, a message naming the secret and the reason, never a value) unless a grant matches all of them, and the kind rule holds: `password` only into `<input type=password>`; `username` and `api_key` only into `<input>` of type text, email, tel, url or password; `text` into an `<input>` or `<textarea>`. The value is written with `fill` on a handle to that element (its current value kept), never to whatever has focus. The origin and path are checked again right before the write (a navigation detaches the handle; a `pushState` doesn't).

**A3, asking.** Approvals are asked when a step is written, which is when the agent grounds it, and again whenever an interactive run (grounding, a re-record in the app) reaches an ungranted step: the runtime pauses at it with its element resolved (a `requestApproval` hook), and the host asks, built from the live page, never from agent-written text (`intent` is not shown): *"Type **acme.password** into this field (screenshot with the resolved element outlined; `input type=password`, label "Password") on **staging.acme.com/login**, for step *sign-in* of the *login* preset?"* Approve / approve for a wider path / decline. Steps are asked in run order. A declined step leaves the scene `blocked`.

**A4, headless.** `kiframe record` and CI never ask: an ungranted use fails the step, with the reason (no grant, target healed, path changed). Grants are per machine; running on another machine (CI) needs the user to export named grants to it (later: BACKLOG), never a field the agent can write. A refusal says which part of the grant stopped matching (never approved, another origin, the target changed, another page, the element changed). A host serving the vault over IPC keeps the refusal's `code` and `reason` (without `reason: no-grant`, an interactive run can't ask).

**A5, clipboard and drag.** While secrets are known in a context: `press` with a paste in any form (Mod/Ctrl/Meta+V, Shift+Insert, Ctrl+Y: macOS "yank", redo on Windows) is refused (an app's own "Copy" button may have put a value in the clipboard). While focus is in a field holding a secret (one a secret was written to, or any input whose value or selected text contains a known value, matched in Node: a re-mounted input keeps its value), `press` takes **only Enter, Tab, Shift+Tab or Escape**: an allowlist, not a denylist (copy, cut, select-all, macOS kill (Ctrl+K), Mod+Insert: editing commands differ per platform). A `drag` is refused when its source holds such a field (across shadow roots). Every spelling of a key Playwright accepts (`ControlOrMeta`, `ControlLeft`, `KeyV`) is normalized first. The context never gets `clipboard-read` / `clipboard-write` permissions, and the runtime never reads or sends the clipboard. Headed runs use the OS clipboard: the host clears it when the context ends.

**A6, interrupts.** A rule whose `do` types a secret is granted like a step; its grant also covers the rule's `when` (a changed `when` asks again). Only `password` secrets in interrupt rules.

**A8, no probing.** While values are known, no locator or condition can test a value (a pass/fail result would leak it one guess at a time): a CSS selector testing the `value` attribute (`[value…]`) is refused, and so is any locator string (a name, a text, a selector) that is part of a known value or contains one (3+ characters, ignoring case). Checked in Node, on every `find`, `waitFor`, `expect` and `ensure`.

**A7, revocation.** The vault UI lists grants per project; removing one makes the step ask again. Removing a secret removes its grants.

## 4. Ownership

- **`@kiframe/vault`:** values (keychain), metadata, grants, `list`, `request`, `grant` / `revoke` (host only), `resolve(name, use)` enforcing A1, A2 and A6.
- **`runtime/secrets`** (new module, the runner's only secret code): the known values, the write (A2), the A5 refusals, the scrubber (I3), field tracking and the text scanner (R1–R8), and the region events. The runner calls it at hooks (step start, before an action, after the action, step end, page switch, run end); nothing else in the runner sees a value.
- **Recorder:** writes the region events as they come (with their own time bounds, §5). **Generators and compositor:** secret regions become masks at render time, straight from the take (not stored in `composition.json`: the composition can only add masks); the compositor applies each region's own `from`/`until`, with no timing rules of its own.
- **Host (desktop app, M4):** approval prompts, the vault UI, the project id, and the scene's complete known values (R6).

## 5. Visual rules (I4)

All times are **source time** (the take's clock); a freeze, a hold or a guide screenshot uses the source time of the frame it shows. "The last complete scan" is global across page switches and popups.

**Regions in the take.** A region is one take event, `sensitive { id, from, until, box(es) }`, written by the runtime with its whole time span: the compositor draws it exactly over `[from, until]`. `why`: `secret-field`, `secret-text`, `blind`. Takes recorded before this format (no `from` / `until`) are refused at render time: re-record them.

- **R1, fields.** The element a secret was written to is blurred from the write until the end of the scene, following it (re-measured at every step boundary and page switch; an unsure measurement keeps the last box).
- **R2, scan scope.** Rendered text nodes (not `display:none` / `visibility:hidden`), `<input>` / `<textarea>` values (not password inputs) and `placeholder`s, in the top document and open shadow roots, in the whole document. Each box is intersected with the visible rect of its clipping ancestors (`overflow` containers) and the viewport: text clipped out of view has no box on screen, but its position is kept for R4. Matched in Node, never in the page (I1): case-insensitive, whitespace-tolerant, per block (a value split across nodes, flex or grid items). Values shorter than 6 characters match as whole words only.
- **R3, complete scans.** The page side of a scan (the text, a stable key per node, and every match's rects) runs in **one synchronous evaluate**: atomic in the page's event loop, so a re-render can't make it inconsistent. A scan is complete when it returned; a failed or timed-out (2 s) one, navigations included, is incomplete: it never ends a region and doesn't count as clean.
- **R4, spans.** Occurrences are grouped per value and per **clipping container** (the nearest `overflow` ancestor, or the viewport). Between two complete scans `p` and `s`, an occurrence is *unchanged* when it's the same node with the same box: it keeps its own box. The *changed* ones of a value in a container (moved, entered, left, or in a node that now holds other text: a virtualized list recycling its rows) are covered over `[p, s]` by the **hull of all their boxes at `p` and at `s`**, extended to the container's edge an occurrence entered or left through. Gone at `s`: covered until `s` plus the capture lag (R8). (Pairing changed occurrences one by one is unreliable when a list recycles its nodes; one hull of the changed ones per container is always right, and a fixed header showing the same value keeps its own box.)
- **R5, cadence and in-between text.** A scan at every step boundary (after the action settles: never an earlier scan's result), on scroll and resize, and at least every 300 ms while recording; one at a time. Between scans, a page-side `MutationObserver` (child lists, `characterData`, the `value` / `placeholder` attributes, and the `class`, `style`, `hidden` and `open` attributes that reveal content: then the element's rendered subtree text, up to 10 kB) **streams** to Node, as it happens, the text of added and changed nodes **that are rendered** when its callback runs (`checkVisibility()`), with the node's key (`exposeBinding`: page text only, never values; a page calling it itself can only send text), so nothing is lost when a document dies. Attributes that aren't shown as text (`alt`, `title`, `href`, `data-*`, `aria-*`) and hidden text are never streamed.
- **R6, known values.** A batch carries the values its scenes resolved to the next ones (they share a session). For a **recording** run, the host gives the runtime, before the scene starts, the values of every secret the scene can use (its steps, its presets even skipped, the project's and org's interrupt rules), plus the environment's other `requiredSecrets` when filled (an unfilled one the scene never types is just not known). Resolving a value outside that set fails the recording: every region is backdated to at most the last complete scan, and no rule depends on values arriving late. A **grounding** run produces no take (only R9 images, self-contained): its known values can grow at any time (a secret the user just provided).
- **R7, blind.** A stretch is blind when evidence is missing: while values are known, no complete scan for over 1 s (a hung page, timeouts), the text stream lost (its binding gone), capture lag over budget (R8), or streamed text showing a known value that no scan accounts for (R5). Streamed text is *accounted for* when its node is still there at the next complete scan `s` and the scan either covered it or found it not rendered; only text that was rendered and then disappeared or changed before `s` without being scanned is unaccounted (a 200 ms toast, a redirect interstitial, a menu opened briefly). Blind from the last complete scan `p` until the next complete one: the rendered video holds the frame at `p` (no cursor or ripples drawn over it). A blind stretch over 3 s becomes a cut. Blind stretches and their cuts are applied after the composition's own cuts and speed changes, and the composition can't shorten or remove them; anchors inside one (a caption, a camera move, a ripple) snap to its edges. The take records it as a `blind` region. An ordinary page load with nothing secret on screen is never blind.
- **R8, capture lag.** Measured per frame: the screencast frame's own timestamp against when it was received, plus one frame. Above the budget (500 ms), the stretch is blind (R7).
- **R9, crops and screenshots.** Model screenshots and fingerprint crops: page scripts paused and animations paused (CDP `Emulation.setScriptExecutionDisabled` and the `Animation` domain), complete scan, screenshot, complete scan, resume; every box of both painted over, in Node. Either scan incomplete: no image (an error the caller sees). Crops of a secret-typing target are taken before its write.
- **R10, keystrokes.** A secret write emits no `key` events; the keystroke overlay shows `••••`.

## 6. Out of scope (v0), stated

Text in `<select>` options, iframes, closed shadow roots, pseudo-elements, canvas, images or video (OCR); display tricks by the page itself (bidi overrides, reordering, glyph-swapping fonts: a hostile same-origin app already has the value); partial displays (`sk_live_…4242`); a value the page itself shows as text (a username in a header) probed by text or label locators one guess at a time (A8 closes the value-attribute and selector-engine oracles, which work on password inputs; a value-dependent refusal would itself be an oracle); secrets into contenteditable fields; secrets on origins not in the secret's list (SSO pages: add the origin); running on another machine without an exported grant; unattended re-records after a secret field was healed (they stop and ask); the OS clipboard during a headed run (cleared at the end); a value shown only by a CSS `:hover` rule (no DOM change) for under 300 ms between scans, not during a step's own action (a tooltip the cursor passes over on its way: the step's end scan sees what the step opened); paste steps in scenes that know a secret (refused: paste is rare in demos, type the text instead); several processes owning one vault file; the target page sending the value it received anywhere; Electron targets' persistent profile. Each is in BACKLOG with its user-visible effect.

## 7. Acceptance tests

The M1-7 exfiltration suite, plus:
- **Authorization:** an ungranted step is refused; the granted step moved after a `goto` to another path is refused; a new scene reusing a deleted scene's ids is refused; a re-grounded target (another label on the same path, same bare input type) is refused; a path with another numeric id matches the normalized pattern; a locator matching two elements is refused; a password into a text input is refused even with a grant; a project rule with an org rule's id doesn't get its grant; a changed interrupt `when` is refused; paste after a secret is known, copy with focus in the secret field, and a drag from it are refused; drag and select-all elsewhere still work.
- **Scanner:** flicker (removed then back) never unblurred; a smooth scroll, a slide-in toast, text scrolling into an inner list and a virtualized list recycling its rows covered in every frame between scans; a 200 ms toast between two scans and a redirect interstitial showing the username give a blind stretch, a redirect showing no value doesn't; text updated in place (`characterData`) is caught; an avatar with `alt="bob@acme.com"`, a hidden account menu and a `mailto:` link re-rendering every 100 ms give no blind stretch; a fixed header showing the value keeps its own box while the page scrolls; a timed-out scan ends nothing; a hung page holds the frame at the last complete scan; an activity feed with ten occurrences, scrolled, stays covered; ordinary scan jitter never produces a blind stretch; a 10k-node page scans within budget.
- **Rendering check:** each case is rendered, and the region's pixels are asserted blurred (or the frame held) in **every frame** where the fixture (whose timeline is known) shows the text; the composition can't remove a secret mask.

## 8. Migration

1. `runner.ts` split first, behaviour unchanged (secret code into `runtime/secrets`).
2. Schema: secret-typing steps need an id and a target without fallbacks or `nth`; `sensitive` events get `from` / `until` and `why: blind`; secret masks leave the composition.
3. Vault: grants (scope, step key, path pattern, exact target, element) replace the field binding; `unbind` goes.
4. Runtime: the A2 write and A5 refusals; the scanner on R2–R9; approvals asked through a `requestApproval` hook any interactive run provides (M2-4 later wires the UI).
5. Recorder, generators, compositor: regions applied as written, masks derived at render time, blind stretches as held frames; the rendering check.
